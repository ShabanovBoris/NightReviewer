# NR-17 — Регрессионный corpus и метрики качества

Статус: PLANNED. Фаза: Qualification. Зависимости: [16](NR-16.md).

## Цель

Измерить полезность review и защититься от очевидных false positives/false approvals.

## Входы и границы

Читать [PRODUCT](../PRODUCT.md), [ARCHITECTURE](../ARCHITECTURE.md), [runtime protocol](../protocols/RUNTIME.md), [development protocol](../protocols/DEVELOPMENT.md) и [DoD](../DEFINITION_OF_DONE.md). Входы: current main SHA, подтверждённое lead назначение, merged evidence зависимостей, spec hash. Если реализация уже частично существует, сначала проверить её и закрывать разницу с ТЗ, а не переписывать.

## Работы

1. Собрать 12 маленьких репозиторных fixtures: 8 seeded actionable defects разных направлений и 4 clean controls.
2. У каждого bug есть reproducer/expected evidence, фиксированный base/head и corrected head; oracle не включать в reviewer prompt.
3. Сделать harness отчёта recall/false positives/provenance и marginal yield replica 1/2/3; сохранять raw и model/prompt hashes.
4. Зафиксировать corpus до qualification, разделить deterministic assertions и stochastic metrics; без cherry-picking удачных runs.

## Контракт и ограничения

Acceptance gates QUALITY в ACCEPTANCE.md. Подсчёт по canonical validated defects, не числу похожих фраз; каждое пропущенное/ложное finding требует независимой evidence triage.

Начальный состав 8 seeded cases (lead подтверждает oracle до benchmark): lost update при конкурентной записи; late-result approval после cancel; чтение mutable HEAD вместо pinned SHA; потеря raw при ошибке parsing; неверный retry после неоднозначного send; тест, который не await-ит async assertion и пропускает настоящий сбой; отсутствие негативного сценария capability isolation при наличии воспроизводимой утечки; нарушение границы backend/domain, воспроизводимо ломающее второй fake backend. Последний case должен доказывать функциональный ущерб, а не предпочтение стиля. Не менее одного case на каждый direction; допускается overlap directions.

Заранее designated high cases: cross-run leak, approval after cancel, wrong-SHA reads. Они все должны быть обнаружены. Остальные severity фиксируются oracle до запуска. Четыре clean controls включают исправленные эквиваленты, намеренно нетривиальную корректную async-логику и harmless style variation. Избегать fixture filenames/комментариев, раскрывающих наличие и местоположение бага. Oracle хранится вне bound snapshot и context ACL.

## Критерии приёмки

- **NR-17-AC1**: Все 12 fixtures воспроизводимы offline и имеют oracle/tests, недоступный runtime reviewers.
- **NR-17-AC2**: Live benchmark на закреплённом candidate покрывает ≥7/8 seeded bugs, все заранее помеченные critical/high seeds и ≤1 blocking false positive на 4 clean.
- **NR-17-AC3**: 100% canonical sources разрешаются в сохранённый raw; отчёт содержит failures и timing.
- **NR-17-AC4**: Повтор benchmark сравнивается по версиям, а не затирает предыдущий неудачный результат.

## Проверки и evidence

- Unit metrics на hand-labeled reports; полный live 12-fixture qualification.
- Проверить одинаковый manifest во всех replicas и отсутствие oracle leakage.
- Приложить команды, exit codes, environment/версии, exact SHA и hashes артефактов. Live-проверки отмечать LIVE, deterministic FAKE/CONTRACT; не подменять одно другим.
- Связать каждый AC с доказательством в PR. Общие проверки — только существующие команды из package scripts; после NR-01 обязательно `bun run verify`.

## Не входит

Не обещать универсальный production recall из маленького корпуса; adaptive replica tuning вне v1.

## Сбои, риски и откат

Если метрики не проходят, lead назначает corrective task; нельзя ослабить порог/удалить fixture без изменения пользовательского scope с записью.
