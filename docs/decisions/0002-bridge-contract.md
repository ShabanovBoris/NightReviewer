## Текущий D40 acceptance contract

- **AC1:** один genuine LIVE request через текущий 6.1.3 bridge, fresh context с уникальным canary, read_fixture tool round-trip через Codex Native2 NR-02 и коррелированный реальный ChatGPT ответ.
- **AC2:** bounded typed observable failure для недоступного connector/tool и cancellation acknowledgement с завершением коррелированного stream. D6 ограничение на фактическое состояние stream сохраняется, пока Lead не заменит его новым решением.
- **AC3:** полная трёхконтекстная canary matrix — deferred hardening; один fresh context и уникальный canary остаются частью AC1.
- **AC4:** документы и evidence должны различать 6.1.3 readiness, user-attested transport binding, исторический 6.1.1 source audit, ограничения harness, NOT_RUN и воспроизводимый следующий шаг.

Следующий шаг после этого документационного assignment: получить отдельное Lead assignment/authorization на адаптацию fail-closed harness к 6.1.3 и bounded LIVE AC1/AC2. До этого никаких LIVE calls или runtime/tunnel/connector изменений. OpenAI's [Secure MCP Tunnel documentation](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) describes an outbound-only client, a private MCP server with no public ingress, and access scoped through Platform organization and ChatGPT workspace context. This supports the tunnel security model; it is not an anonymous-request test of the configured DEV tunnel or evidence that it owns a Responses turn.

The spike request uses `Authorization`, `Accept`, and `Content-Type` headers, puts native turn metadata in the JSON body, sets `stream: true`, and uses `previous_response_id` plus `function_call_output.call_id` for the second leg. These remain proposed harness inputs; no qualifying `/v1/responses` request has been observed live.

The three-context harness emits a digest-bound sanitized trace per session. Each ordered SSE frame records its event identity, bounded response/item/call IDs, raw data byte length, and SHA-256 digest without retaining model text or function arguments. The enclosing trace records timestamps and elapsed time for each Responses leg and the fixture read, plus the fixed tool identity, fixture/tool-output hashes, validated structured result, and canary-isolation observations. `liveTraceSha256` is SHA-256 over the exact UTF-8 bytes of `JSON.stringify(liveTrace)`; each SSE trace is limited to 512 frames and 1 MiB of raw frame/event-name bytes, and incomplete capture cannot yield a passing session. These fields describe the runnable evidence format; no live receipt has been collected yet.

### Поддержка, ограничения и текущая проверка

- **Поддерживается исходным кодом 6.1.1:** health/model discovery; streaming `POST /v1/responses`; continuation через `previous_response_id` и исходный `call_id`; turn identity из `x-codex-turn-metadata`; адресное прерывание по `threadId`/`turnId`; typed `connector_not_found`.
- **Не поддерживается DEV-профилем:** точный upstream отвергает запуск Responses listener для `purpose=dev-harness`. Репозиторный DEV chat выдаёт только simulated tool receipts; они не доказывают внешний callback.
- **Не проверено LIVE:** реальный Responses/tool round-trip, чтение fixture, каталог/effort точного runtime, отмена, unavailable connector и изоляция трёх сессий. Подключённый DEV tunnel сам по себе не предоставляет этому harness turn owner.
- **Lead D2/D3/D4 и пользовательское разрешение:** ограничения D2 на превращение DEV в Responses owner и на переиспользование его ресурсов остаются в силе. D3 одобрил отдельный production-профиль из точного pin и schema-valid post-setup override только полей `automaticAppName` и `appName` на `Codex Native2 NR-02`; `manualAppName` остаётся неизменным. Обычный setup перезаписывает имя на `Codex Native2` и не имеет CLI-параметра имени, поэтому после override нужно повторно разобрать config штатным `parseConfig`, запустить pinned production supervisor и подтвердить health/version/identity. Это spike-specific конфигурационный путь, а не заявленная upstream установка произвольного имени. D4 разрешил DEV diagnostics без изменения существующих tunnel credentials, connector identity или permissions. Пользователь позднее разрешил применять обычный DEV для всей разработки, а lead подтвердил постоянный охват; этот scope не превращает `purpose=dev-harness` в Responses owner и не квалифицирует simulated receipts. Текущий `dev status` показывает `mcpRuntime.ready=false`, `state=starting`. Поскольку DEV tunnel принадлежит launcher supervisor, standalone `tunnel restart` к нему неприменим. `dev setup --full` остановился до сохранения профиля, потому что launcher ChatGPT session не верифицировалась. The exact-pin production Launcher has a source-supported shutdown path through normal Quit, which drains and stops the isolated tunnel/daemon and closes its browser workers; this path still needs live verification.
- **Открытый внешний prerequisite:** D3 требует полностью новые `CODEX_CHATGPT_WEB_HOME`, `CODEX_HOME`, `CODEX_WEB_GPT_LAUNCHER_DATA_DIR` и browser profile, отдельные Tunnel/runtime key и connector `Codex Native2 NR-02`, loopback-only Responses endpoint, а также подтверждение, что DEV и shared 6.1.2 ресурсы не читались, не переиспользовались и не менялись. Этот production профиль не создан и его unique connector ownership не подтверждена; AC1–AC3 остаются `BLOCKED`.

### Решение spike

Provisional approach: use the local Responses route plus a thin outer driver to measure the wire contract. Keep this code under `spikes/bridge` and `scripts/`; do not export it from the product API or treat it as the production `ReviewerBackend`. The driver declares only the fixture directory as its read-only workspace, accepts one symbolic fixture key, and uses three generated session identities. It fails closed on non-loopback endpoints and on a bridge version other than `6.1.1`. D3 documented the former independently owned exact-pin production-profile route; D40 changed the current acceptance baseline to 6.1.3.

### Lead D5: unavailable-connector failure injection

Lead decision `NR-02-D5-TEMPORARY-ISOLATED-MISSING-CONNECTOR-PROBE` authorizes one bounded unavailable-connector LIVE probe after the isolated D3 profile is healthy with its normal `Codex Native2 NR-02` identity. Stop only that profile, temporarily set only `appName` and `automaticAppName` to the same unique nonexistent connector identity, validate with the pinned parser, restart through its normal supervisor, and send exactly one synthetic Responses request. A qualifying result is the real typed `424 connector_error/connector_not_found` response. Immediately stop the profile, restore the two identity fields to `Codex Native2 NR-02`, validate again, restart, and verify exact-pin health and restored identity. Keep `manualAppName`, permissions, tunnel settings/ID, key paths, browser paths, runtime command, and credentials unchanged. Do not alter or disable a real connector.

This procedure and decision are source-bounded to the isolated D3 config; they do not change D2/D3 ownership or qualify DEV results. The method is now documented, but the probe result is `NOT_RUN`: the separate D3 profile is not ready and the unique connector has not been created. NR-02-AC2 still needs both this unavailable outcome and a separate cancellation outcome. Lead's decision receipt is bound by message `1d43d86f-4c70-43e5-9d45-c952a3ff0e6c`; its response SHA-256 is `5ccbec8e31b743ce9a584e43bc3fa44bc5d29c33188b3a1469071b18a5f0a591`.

### Lead D6: cancellation evidence contract

Lead decision `NR-02-D6-ACK-PLUS-CORRELATED-STREAM-TERMINATION` selects `ACK_PLUS_STREAM_TERMINATION`. It classifies the cancellation evidence only; it does not authorize a live cancellation probe. Run only against the D3 production profile proven to be the exact `6.1.1` pin, with one newly generated synthetic `threadId`/`turnId` and no unrelated probe turns. Before interrupting, observe exactly one active HTTP turn and confirm that the correlated stream has not already terminated. Send `POST /admin/interrupt-turn` with that same identity and require HTTP `200`, JSON `status=ok`, and `cancelled_http_turns=1`.

The correlated Responses stream must then terminate within 10 seconds of the successful control acknowledgement and must not contain `response.completed` before or after the interrupt. Record the request identity and timestamps for Responses start, interrupt request, acknowledgement, and stream termination. Preserve the sanitized typed control acknowledgement separately from the parser's actual stream disposition: explicit `response.failed`, `response.incomplete`, clean EOF/incomplete parse, and read cancellation/error remain distinguishable. A clean EOF or parser-classified incomplete outcome is qualifying only with the exact successful acknowledgement and no observed completion. An explicit `response.failed` with client-cancellation semantics is stronger evidence but is optional. Never synthesize `response.failed` or a `cancelled` SSE result from a clean EOF or read error.

An acknowledgement without observed stream termination, HTTP status other than `200`, malformed acknowledgement, wrong identity/count, a stream already terminal before interrupt, `response.completed`, or timeout fails this probe. The D6 receipt is correlated as `a4b0f8e6-42be-4e08-a75d-1a4dd5bde69a` → request `39a5cdea-ebac-49da-9eb3-e28f19e3a75c`; the sanitized raw response SHA-256 is `440af0e7bf37accfd47cbdef24cde1c20b106bac833275b8dcfefaf8235d3174`. AC2 remains `BLOCKED` until both the D5 unavailable-connector and D6 cancellation LIVE outcomes are observed; D6 alone does not change AC1 or AC3.
