# NR-11 — Независимые replica и направления

Статус: PLANNED. Фаза: Web MVP. Зависимости: [10](NR-10.md).

## Цель

Запускать strict 3×3 с воспроизводимыми prompts и независимыми свежими чатами.

## Входы и границы

Читать [PRODUCT](../PRODUCT.md), [ARCHITECTURE](../ARCHITECTURE.md), [runtime protocol](../protocols/RUNTIME.md), [development protocol](../protocols/DEVELOPMENT.md) и [DoD](../DEFINITION_OF_DONE.md). Входы: current main SHA, подтверждённое lead назначение, merged evidence зависимостей, spec hash. Если реализация уже частично существует, сначала проверить её и закрывать разницу с ТЗ, а не переписывать.

## Работы

1. Добавить versioned correctness/tests/design prompts и explicit scope/coverage instructions.
2. Фиксировать prompt/model/policy hashes в manifest; один prompt внутри направления для всех replica, без чужих outputs.
3. Реализовать fair wave-like dispatch 3 направлений × 3 replicas при общей concurrency 3.
4. Публиковать progress по direction/replica, сохранять все raw attempts и explicit missing runs.

## Контракт и ограничения

Replica independence = fresh chat/history + same snapshot/prompt + no access to other reports. Account memory/settings проверить spike/canary; факт fresh tab сам по себе недостаточен.

## Критерии приёмки

- **NR-11-AC1**: Strict профиль создаёт ровно 9 выбранных complete replica reports с уникальными run IDs.
- **NR-11-AC2**: Все replica одного direction имеют одинаковые prompt/context hashes и разные session identities.
- **NR-11-AC3**: Инъекция чужого run ID/history/tool доступа не открывает соседние findings.
- **NR-11-AC4**: Отказ одного обязательного reviewer блокирует approval; aggregation не стартует по частичному набору.

## Проверки и evidence

- Fake 3×3 scheduler deterministic coverage и interleaving.
- Live 3 одинаковых reviewer-а на одном fixture, затем один strict 3×3 smoke; raw receipts сохранены.
- Приложить команды, exit codes, environment/версии, exact SHA и hashes артефактов. Live-проверки отмечать LIVE, deterministic FAKE/CONTRACT; не подменять одно другим.
- Связать каждый AC с доказательством в PR. Общие проверки — только существующие команды из package scripts; после NR-01 обязательно `bun run verify`.

## Не входит

Без adaptive replicas или обещания, что каждый повтор найдёт уникальный баг.

## Сбои, риски и откат

Общий browser cap учитывает shared pool: при занятых upstream slots ожидать bounded queue, не увеличивать cap. Rollback profile version не меняет уже принятые reviews.

## Поставка

Один bounded PR `[NR-11] Независимые replica и направления` в `main`, включающий код, релевантные тесты, документацию поведения/миграции и evidence index. Пройти reviewer → fix verification → lead merge authorization по точным SHA. После merge проверить resulting main и отправить TASK_COMPLETED. Если lead разбивает задачу, все child PR проходят тот же цикл, родитель завершается только после всех AC. Открытый PR не означает выполненное ТЗ.
